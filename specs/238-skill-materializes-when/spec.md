# Feature Specification: record per-skill materialization conditions on the product skill-manifest

**Feature Branch**: `238-skill-materializes-when`

**Created**: 2026-07-04

**Status**: Draft

**Input**: Resolves cross-repo request **FS-GG/FS.GG.Rendering#71** — the **P1 Rendering** child of
epic **FS-GG/.github#163** (ADR-0017: org skill registry + condition-aware materialization).
Owner-confirmed resolution direction: **record honestly** (drop-from-effective-set), not
supply-in-sdd. Cross-repo companions: **FS-GG/.github#164** (`registry/skills.yml` +
`skill-registry` contract + validator + gate `--params`) and **FS-GG/FS.GG.SDD#53** (process
manifest / the `fs-gg-project` seam on the SDD side).

## Context (non-normative)

The product skill-manifest (`template/skill-manifest/skill-manifest.json`, ADR-0014 §Decision 1) is
a **superset catalog**: it declares every product-scope skill the template *can* emit, each with a
canonical-body `sha256`, and ships **ungated** (the `template/skill-manifest/` source in
`.template.config/template.json` fires in every lifecycle). Whether a given skill's *body* actually
materializes is decided elsewhere — by the `profile` / `lifecycle` / `feedback` **conditions on the
per-skill sources** in `template.json`. The manifest records the digest but **not** that condition, so
`declared ∧ absent` is indistinguishable from a supply failure. The skill-union assertion therefore
treats every gap as legitimate (the superset-catalog rule).

That blanket tolerance hides one genuine bug. `fs-gg-project` is declared `scope: product` and its
*only* body source is the base agent tree (`template/base/.agents/`, gated
`lifecycle == "spec-kit"`) — it is **not** among the `template/product-skills/*` sources. Under the
`lifecycle=sdd` lane (`new-sdd-fullstack`, `profile=game lifecycle=sdd`), Rendering never emits it,
and SDD's `SeededSkills.skillNames` **deliberately excludes** the product-internal project skill. Net:
in the sdd lane `fs-gg-project` is **declared by the manifest and supplied by nobody** — verified
absent from all three skill roots of the shipped `SpaceInvaders`/`SpaceInvaders1` products, yet
tolerated because the gate cannot see the missing emission condition.

The manifest is machine-generated by `scripts/generate-skill-manifest.fsx` (a hard-coded
`id → canonical-source` catalog; `schemaVersion: 1`; entries `{id, scope, sha256, resolvablePath}`),
and `tests/Package.Tests/Feature231SkillManifestTests.fs` recomputes the digests and fails on drift.
This feature extends that producer and its test — it does **not** change any emission behavior: the
same skills materialize in the same lanes as today.

### Scope boundary (cross-repo)

- **This feature (Rendering, P1):** add the emission condition to each manifest entry and regenerate.
  Backward-compatible/additive — no change to *which* skills emit in *which* lane.
- **Out of scope — FS-GG/.github#164:** the authoritative `registry/skills.yml`, the `skill-registry`
  governed contract, its validator, and tightening `skill-union-assert.sh` to enforce the new
  `[missing]` / `[unexpected]` classes when passed `--params scaffold-provenance.json`. This feature
  only makes the enforcing input *available* and *honest*; it does not itself flip any gate.
- **Out of scope — FS-GG/FS.GG.SDD#53:** the SDD process manifest and the sdd-lane owner decision on
  the project skill. Rendering records the truth (`fs-gg-project` is a `spec-kit`-lane skill); SDD
  stops implying it in the sdd-lane effective set.

## Requirements (normative)

- **FR-001 — per-entry `materializes-when`.** Every entry in
  `template/skill-manifest/skill-manifest.json` gains a `materializes-when` field carrying the boolean
  condition under which that skill's body is emitted. The value MUST be the exact condition the
  template applies to that skill's body source in `.template.config/template.json` (single source of
  truth), namely:

  | id | `materializes-when` |
  |---|---|
  | `fs-gg-project` | `lifecycle == "spec-kit"` |
  | `fs-gg-scene` | `profile == "app" \|\| profile == "headless-scene" \|\| profile == "governed" \|\| profile == "sample-pack" \|\| profile == "game"` |
  | `fs-gg-symbology` | `profile == "app" \|\| profile == "headless-scene" \|\| profile == "governed" \|\| profile == "sample-pack" \|\| profile == "game"` |
  | `fs-gg-skiaviewer` | `profile == "app" \|\| profile == "sample-pack" \|\| profile == "game"` |
  | `fs-gg-elmish` | `profile == "app" \|\| profile == "sample-pack" \|\| profile == "game"` |
  | `fs-gg-keyboard-input` | `profile == "app" \|\| profile == "game"` |
  | `fs-gg-ui-widgets` | `profile == "app" \|\| profile == "game"` |
  | `fs-gg-styling` | `profile == "app" \|\| profile == "game"` |
  | `fs-gg-layout` | `profile == "app" \|\| profile == "game"` |
  | `fs-gg-testing` | `profile == "governed"` |
  | `fs-gg-samples` | `profile == "sample-pack" && lifecycle == "spec-kit"` |
  | `fs-gg-feedback-capture` | `feedback == true && lifecycle == "spec-kit"` |

- **FR-002 — per-entry `supplied-by`.** Every entry gains a `supplied-by` field naming the provider
  source directory that emits its canonical body (the generator already knows this — it is the
  catalog's source path, minus the `SKILL.md` leaf): `fs-gg-project` →
  `template/base/.agents/skills/fs-gg-project/`; each product skill → `template/product-skills/<id>/`;
  `fs-gg-samples` → `template/fragments/samples/skill/`; `fs-gg-feedback-capture` →
  `template/feedback/skill/`.

- **FR-003 — `fs-gg-project` recorded honestly.** `fs-gg-project`'s `materializes-when` is
  `lifecycle == "spec-kit"`, which — evaluated against the sdd-lane params
  (`lifecycle=sdd`) — is **false**, so the entry is `declared ∧ condition-false ∧ absent`
  (legitimately suppressed) rather than the untyped `declared ∧ absent` it is today. This is the
  single record that lets the downstream gate distinguish this skill from a genuine supply failure.

- **FR-004 — additive / backward-compatible schema.** The two new fields are **optional additions** to
  ADR-0014's `{id, scope, sha256, resolvablePath}` shape. Existing consumers that ignore unknown keys
  MUST keep working unchanged. The condition strings use the same grammar as `template.json` source
  conditions so an evaluator can reuse the existing conditional engine.

- **FR-005 — generator is the single producer.** `scripts/generate-skill-manifest.fsx` emits the two
  new fields for every entry; the on-disk manifest is fully regenerated from it. The `--check` mode
  still fails when the on-disk manifest drifts from the generator's output (now including the new
  fields).

- **FR-006 — no drift between manifest and template.json.** Each entry's `materializes-when` MUST stay
  equal to the condition `template.json` applies to that skill's body source. This equivalence MUST be
  enforced by a test (extending `Feature231SkillManifestTests` or a sibling), so a future edit to a
  `template.json` source condition that is not reflected in the manifest fails the build.

- **FR-007 — no emission-behavior change.** No `template.json` source, condition, profile, or gate is
  changed such that a different set of skills materializes in any lane. The existing lifecycle/profile
  package tests (Feature 204 / 219 / 231) stay green; the shipped scaffolds' materialized skill sets
  are byte-identical to today. `fs-gg-project` remains emitted only in the `spec-kit` lane (unchanged);
  this feature records that fact, it does not alter it.

## Success Criteria

- **SC-001** — The regenerated `skill-manifest.json` carries `materializes-when` + `supplied-by` on all
  12 entries, with values matching the FR-001/FR-002 tables exactly; `generate-skill-manifest.fsx
  --check` reports up-to-date.
- **SC-002** — A discriminating test asserts, per entry, that `materializes-when` equals the condition
  on that skill's `template.json` body source (a stale/duplicated string fails it), and that
  `fs-gg-project`'s condition evaluates **false** under `lifecycle=sdd` params and **true** under
  `lifecycle=spec-kit`.
- **SC-003** — Backward compatibility proven: a consumer reading only `{id, scope, sha256,
  resolvablePath}` sees identical values to the pre-feature manifest (the digests and paths are
  unchanged; only new keys are added).
- **SC-004** — No behavioral regression: the Package.Tests lifecycle/profile suites (Feature 204 / 219
  / 231) are green and the materialized skill set of a freshly scaffolded product is unchanged in both
  the `spec-kit` and `sdd` lanes.
- **SC-005** — Issue #71 can be closed against this manifest: the `.github#164` union gate, once it
  reads these conditions with sdd-lane params, would classify `fs-gg-project` as legitimately
  suppressed (not `[missing]`), and any *actually* missing-but-required skill as `[missing]`.

## Assumptions

- The manifest stays hand-free: it is only ever produced by `generate-skill-manifest.fsx`, never
  edited directly (existing convention).
- Whether to keep `schemaVersion: 1` (purely additive optional fields) or bump it is an implementation
  decision for `/speckit-plan`; either satisfies FR-004 as long as unknown-key-tolerant consumers are
  unaffected. Preference: keep `1` (additive), matching ADR-0017's "additive to ADR-0014".
- The condition-string format the `.github` validator/gate consumes is the `template.json` source
  condition grammar; ADR-0017 states "for Rendering it is literally the `template.json`
  `sources[].condition`", so no re-encoding into a different expression language is required here.
- The exact YAML/JSON schema for `registry/skills.yml` is owned by `.github#164`; this feature's job is
  to make Rendering's producer manifest the honest input to that generation step, not to define the
  registry format.
- `fs-gg-project`'s body source is the whole gated base agent tree (`template/base/.agents/`), not a
  per-skill source, so its `materializes-when` is that tree's condition (`lifecycle == "spec-kit"`);
  mapping a tree-level condition to the one skill inside it is handled in the generator's catalog
  (the plan will decide whether to derive it from `template.json` or assert equivalence in the test).
